# CloudPulse Governance

CloudPulse is maintained as an open-source project in the NAU-OSS organization.

This document explains how decisions are made and how contributors can participate.

## Project Principles

CloudPulse follows these principles:

1. Keep the core understandable.
2. Prefer focused solutions over unnecessary complexity.
3. Discuss significant changes publicly.
4. Make contribution paths clear.
5. Treat tests and documentation as important project work.
6. Maintain respectful technical discussion.

## Roles

### Users

Users run CloudPulse and provide feedback about bugs, usability problems, and feature ideas.

### Contributors

Contributors improve the project through code, documentation, testing, issue reports, reviews, or technical discussion.

No formal role is required before contributing.

### Maintainer

The maintainer is responsible for reviewing contributions, organizing the repository, resolving technical decisions, maintaining releases, and enforcing project standards.

## Decision Making

Small changes can normally be discussed directly in issues or pull requests.

Changes affecting command-line behavior, architecture, security, compatibility, or project scope should normally begin with a GitHub issue.

Technical decisions should consider:

- usefulness
- implementation complexity
- maintainability
- testability
- compatibility
- security
- project scope

When consensus cannot be reached, the maintainer makes the final repository decision while documenting the reasoning publicly.

## Pull Requests

Pull requests should:

- focus on one logical change
- explain what changed
- explain why it is needed
- include tests when appropriate
- update documentation when behavior changes
- pass CI before merge

## Growing Contributor Responsibility

Repeated high-quality participation builds trust.

Contributors who consistently provide useful issues, reviews, documentation, tests, or code may be given greater responsibility as the project grows.

## Community Standards

All contributors must follow `CODE_OF_CONDUCT.md`.

Technical disagreement is welcome. Harassment and personal attacks are not.

## Security

Security-sensitive reports should follow `SECURITY.md`.

## Governance Changes

This governance model may evolve as the project grows.

Significant governance changes should be proposed publicly and documented.
